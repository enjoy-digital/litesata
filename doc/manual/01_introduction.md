# Introduction {#introduction}

This chapter says what LiteSATA is, why it exists, what it does and what it does not do. It ends
with the layout of the repository and a map of the manual. Every reader should start here.

## What the project is {#intro-what}

LiteSATA connects an FPGA design to a SATA hard disk or SSD. It plays the role of the SATA host:
it wakes up the link, exchanges frames with the drive and runs read, write and identify commands
on it. User logic sees simple streams of commands and sector data, and never handles the protocol.

The project has four parts, shown in the figure below. The PHY drives the FPGA transceiver and
brings the link up. The core implements the link, transport and command layers of SATA. The
crossbar shares the core between user ports, and the frontends give user logic and the CPU
ready-made engines: Identify, BIST, DMAs and streams.

![LiteSATA at a glance. User logic and the frontends reach the drive through the user ports of
the crossbar; the core runs the commands and frames them; the PHY drives the transceiver. A CPU
and the LiteX BIOS use the frontends through registers.](intro_overview.svg)

The gateware is written in Python with Migen and LiteX, and generates Verilog for the FPGA tools.
It can be used as a LiteX library, usually through the `add_sata` method of a LiteX SoC, or as a
standalone Verilog core generated by `litesata_gen` from a YAML configuration (see
[Integration](#integration)).

## Why LiteSATA {#intro-why}

A SATA drive is usually reached through a host controller chip on a PCIe bus, with an AHCI driver
on a processor. LiteSATA needs neither: the FPGA transceiver talks to the drive over a SATA cable,
and the whole host runs in the FPGA fabric. A design can stream data to a drive with no CPU at all.

The core is small and has one job: move sectors between user logic and the drive. It implements the
three ATA commands such a design needs and the parts of SATA they rely on, and nothing more. Every
layer can be read in one sitting, simulated against a Python drive model, and extended.

One core runs on every PHY, as the figure below shows. The PHYs share one interface to the core
and one controller for the link bring-up, with an ECP5 variant of its ALIGN hand-off; otherwise
only the transceiver wrapper and its clocking change from one FPGA family to the next.

![One core, many PHYs. The same core and frontends run on the Xilinx GTP, GTX, GTH and GTY
transceivers and on the Lattice ECP5 DCU; each PHY wraps one transceiver
family.](intro_phys.svg)

LiteSATA records data at the rate of real applications. The LiteX-M2SDR board of Enjoy-Digital, an
Artix-7 software-defined radio, uses it to record radio samples to a Samsung 850 EVO SSD in real
time ([Performance and resources](#perf-measured) gives the measured figure).

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| PHYs | Xilinx Artix-7 GTP, Kintex-7 GTX, UltraScale GTH, UltraScale+ GTH and GTY; Lattice ECP5 DCU |
| Rates | Gen1 (1.5 Gbps), Gen2 (3 Gbps) and Gen3 (6 Gbps), fixed when the design is built; Gen2 only on ECP5 |
| Link bring-up | COMRESET, COMINIT and COMWAKE out-of-band signalling, in the transceiver on Xilinx and in the fabric on ECP5; byte alignment on K28.5; automatic RX polarity detection |
| PHY datapath | 16- or 32-bit transceiver interface, 32-bit core interface, link monitor with connect and disconnect events |
| Link layer | ALIGN insertion and removal, CONT removal, scrambling, CRC, HOLD flow control, error reporting |
| Transport and commands | Register, DMA Activate, PIO Setup and Data FISes; READ DMA EXT, WRITE DMA EXT and IDENTIFY DEVICE; 48-bit LBA |
| Frontends | Crossbar with round-robin arbitration and 32- or 64-bit user ports; Identify; BIST generator and checker; Wishbone DMAs between sectors and memory; sector streams; striping (RAID0-like) and mirroring (RAID1-like) |
| Software | LiteX BIOS commands (`sata_init`, `sata_read`, `sata_write`), boot from a FAT file system on the drive, bench host scripts |
| Integration | LiteX library (`add_sata`), or standalone Verilog core from `litesata_gen` with native ports or a Wishbone or AXI-Lite control bus and a Wishbone DMA master |
| Verification | Unit tests of every layer against a Python model of a drive |

## Supported FPGAs {#intro-fpgas}

The table below lists the PHYs, the type of transceiver they drive, their rates and their state.
[Supported FPGAs and boards](#boards) gives the boards, [Xilinx transceiver PHYs](#xilinx-phys)
and [Lattice ECP5 PHY](#ecp5-phy) the details of each family.

| FPGA family | Type | PHY | Rates | Width | State |
|---------------|------|--------------------------|-------------|-------|------------|
| Artix-7 | GTP | `A7LiteSATAPHY` | Gen1 to Gen3 | 16, 32 | Validated |
| Kintex-7 | GTX | `K7LiteSATAPHY` | Gen1 to Gen3 | 16, 32 | Validated |
| Kintex, Virtex UltraScale | GTH | `GTH3LiteSATAPHY` | Gen1 to Gen3 | 16, 32 | Validated |
| UltraScale+ | GTH | `GTH4LiteSATAPHY` | Gen1 to Gen3 | 16, 32 | Validated |
| UltraScale+ | GTY | `GTY4LiteSATAPHY` | Gen1 to Gen3 | 16, 32 | Validated |
| Lattice ECP5-5G | DCU | `ECP5LiteSATAPHY` | Gen2 | 16 | Validated at Gen2 |

*Validated* means validated on hardware: the PHY has brought a link up with a real drive and run
commands on it. *Width* is the width of the transceiver interface in bits; the core is 32 bits
wide on every PHY. Users do not name the PHY class: `LiteSATAPHY` picks it from the FPGA part
number.

UltraScale+ covers the Artix, Kintex, Virtex and Zynq UltraScale+ families. The GTY PHY is the
default; a design with GTH transceivers selects the GTH PHY with `gt_type="GTH"`, as the ZCU102
target does, and Artix UltraScale+ parts always get the GTH PHY.

The highest Artix-7 rate depends on the speed grade of the part: LiteX-Boards limits the Nexys
Video, a -1 speed grade board, to Gen2.

The ECP5 has no out-of-band signalling in its transceiver, so the ECP5 PHY generates and detects it
in the fabric. It needs an ECP5-5G part (`LFE5UM5G`) and runs at Gen2 only.

## What it is not {#intro-limits}

LiteSATA is a host for one drive per link, built for FPGA designs that move sectors. It does not
implement the parts of SATA and ATA that such designs rarely need:

- No device mode: LiteSATA is always the host, and cannot make the FPGA look like a drive.
- No AHCI and no operating system driver: software uses the registers of the frontends, as the
  LiteX BIOS does.
- Three commands only: READ DMA EXT, WRITE DMA EXT and IDENTIFY DEVICE. There is no NCQ, no FLUSH
  CACHE and no TRIM.
- 512-byte logical sectors only.
- No port multiplier: the port field of every FIS is 0.
- No power management: the link never enters the partial or slumber states.
- No rate fallback on the host side: the rate is fixed when the design is built. A faster drive
  steps down to it; a drive slower than the host rate never links.
- No retry at the link or command level, and no command timeout in the core: a failed command is
  reported to the user port, and the user or the software decides what to do.
- No PHY for Intel (Altera) or other FPGA vendors, no ECP5 Gen1 or Gen3, and no ECP5 PHY in the
  standalone generator.

The chapters of Parts II and III list the limits of each layer and PHY where they matter.

## Repository layout {#intro-layout}

| Path | Content |
|------------------------------|---------------------------------------------------------------|
| `litesata/phy/` | The PHYs: transceiver wrappers per family, the link bring-up controller, the datapath |
| `litesata/core/` | The core: link, transport and command layers |
| `litesata/frontend/` | Crossbar, Identify, BIST, DMAs, streams, striping and mirroring |
| `litesata/common.py` | Primitives, FIS layouts, ATA command codes and stream layouts of all layers |
| `litesata/gen.py` | The standalone generator `litesata_gen` |
| `bench/` | Bench targets of eight boards and their host scripts (`test_init.py`, `test_bist.py`, `test_dma.py`) |
| `examples/` | Configuration files of the generator |
| `test/` | Unit tests and the Python drive model (`test/model/`) |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`), photos and the generator notes |

The BIOS commands and the SATA library are not in this repository: they are part of the LiteX
BIOS, in `litex/soc/software/liblitesata/` and `litex/soc/software/bios/cmds/cmd_litesata.c` of
the LiteX repository.
